# 开源调研：约束生成 / 结构化输出方向

> 调研日期 2026-10-13；star 数为当日 GitHub 实测值。选型结论：**思想借用、轻量自建**——内部约束层必须与私有平台 schema 深度耦合，引入重框架的学习/部署成本大于收益。

## 1. Outlines（dottxt-ai/outlines）⭐ 15.9k

https://github.com/dottxt-ai/outlines

- **核心思想**：把 JSON Schema / 正则编译为受限解码 grammar，在采样层面保证输出 100% 合法（only valid tokens can be sampled）。
- **借用点**：本项目"结构合法率 100% 是硬指标"的目标设定；"约束前移到生成阶段优于事后修补"的原则（`schema.py` 结构层先拦，业务层后检的分层次序）。
- **不采用原因**：作用于开源模型本地推理（transformers/vLLM）；生产走 Claude API 时无法干预采样层。API 场景下等价能力由 tool use / structured output 承担，本仓库以真实 API + 分层校验在应用层逼近该保证。

## 2. Instructor（567-labs/instructor）⭐ 14.0k

https://github.com/567-labs/instructor

- **核心思想**：Pydantic 模型 → 结构化输出 + **校验失败自动重试回喂**（`max_retries` 内 reask，错误信息随提示回传）。
- **借用点**：本项目的校验-修复循环直接对标其 reask 模式——`generator.py` 的反馈回喂、重试上限、以及"重试耗尽显式降级"的补强（Instructor 抛异常，本仓库把降级做成产品功能并附完整失败原因）。
- **不采用原因**：其校验绑定 Pydantic 类型系统，表达不了引用完整性/双端矩阵/套餐白名单这类跨配置树与外部注册表的约束。

## 3. Guidance（guidance-ai/guidance）⭐ 21.8k

- **核心思想**：模板语言把生成约束为"语法骨架 + 填空"，枚举值可直接注入 grammar（`select()`）。
- **借用点**：第三层"合法枚举注入"——把注册表枚举喂进生成上下文；本项目进一步把枚举写进**结构化错误信息的 options 字段**，让纠错信息本身携带合法值。
- **不采用原因**：绑定特定推理栈与 prompt 模板；与 Claude API 的 tool use 路线冲突。

## 4. Guardrails AI（guardrails-ai/guardrails）⭐ 7.5k

https://github.com/guardrails-ai/guardrails

- **核心思想**：输出 → Validator 链（结构/语义/自定义）→ 不合格带结构化错误 reask；Validator 可组合、错误可机读。
- **借用点**：`violations.py` 的 Violation 结构（code/path/message/options/layer）与四层校验器组织方式；"校验器是可回归测试的第一公民"——每个 validator 对应确定性测试。
- **不采用原因**：框架较重（含服务端与远程验证器），与"千行级内聚约束层"的定位不符。

## 5. python-jsonschema（python-jsonschema/jsonschema）⭐ 5.0k

https://github.com/python-jsonschema/jsonschema

- **核心思想**：JSON Schema 标准校验的参考实现。
- **借用点**：结构层校验的字段/类型/必填/枚举语义；内部 schema 文档化后（逆向整理完成），`schema.py` 可替换为 schema 文件 + 该库，校验语义不变。
- **暂不直接采用原因**：内部 schema 尚无正式文档（源报告加重因素第一条），先用代码内建校验器钉住契约、避免"先编一份没人对过账的 schema 文件"。

## 6. python-json-patch（stefankoegl/python-json-patch）⭐ 497

https://github.com/stefankoegl/python-json-patch

- **核心思想**：RFC 6902 JSON Patch 的 Python 实现（add/remove/replace/move/copy/test）。
- **借用点**：patch 语义与 op 集合（本仓库取 add/remove/replace/move 子集）；在其上叠加**白名单、manual_locked 锁、根替换禁止、原子回滚**四层防护——这是开源库没有、而"增量编辑安全"必须有的部分。
- **不采用原因**：库本身无约束概念（拿到 patch 就应用），恰是失败模式 6 的成因；防护必须在引擎层自建。

## 7. XGrammar（mlc-ai/xgrammar）⭐ 2.0k

https://github.com/mlc-ai/xgrammar

- **核心思想**：高效上下文无关 grammar 约束解码引擎（适配 schema 到 token 级 mask）。
- **借用点**：调研储备——若未来切自托管开源模型，结构层保证从"校验+重试"升级为"采样级保证"，XGrammar 是候选引擎。
- **不采用原因**：同 Outlines，需本地推理栈。

## 结论矩阵

| 需求 | 采用方案 | 思想源头 |
|---|---|---|
| 结构 100% 合法 | 分层校验 + 结构违规先行拦截 | Outlines/XGrammar（约束前移） |
| 错误可纠正 | 结构化反馈 + reask 循环 + 降级 | Instructor/Guardrails |
| 枚举不幻觉 | 注册表注入 + options 回喂 | Guidance |
| 增量编辑安全 | 受约束 patch 引擎 | RFC 6902 / python-json-patch |
| 改动不回归 | golden 评测集 + 指标 | Guardrails/Evals 惯例 |
