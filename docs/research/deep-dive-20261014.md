# 自主深潜研究 · 2026-10-14：repair 类不收敛的根因解剖与模型能力上限

研究方法：每轮提出一个可实验验证的问题 → 最小实验（真实 LLM）→ 数据结论。
模型：glm-4-flash（基线小模型）与 glm-5.3-flash（reasoning 强模型），端点
`NL2CONFIG_BASE_URL`（OpenAI 兼容）。全部原始数据：`evidence/*-20261014*.json`。

---

## Q1：换强模型（glm-5.3-flash）能否解决 v2 prompt 下 repair 类（05/07/08）不收敛？

**假设**：若失败源于管线/反馈机制缺陷，强模型也会失败；若源于模型能力，强模型应收敛。

**实验**：`NL2CONFIG_TIMEOUT=300` + glm-5.3-flash 全量 golden（8 对，max_retries=3）。
复现：

```bash
NL2CONFIG_API_KEY=... NL2CONFIG_BASE_URL=... NL2CONFIG_TIMEOUT=300 NL2CONFIG_CALL_INTERVAL=2 \
python3 evidence/collect_golden_detail.py evidence/golden-glm53-20261014.json --model glm-5.3-flash
```

**数据**（`evidence/golden-glm53-20261014.json`）：

| 指标 | glm-4-flash（10-13 v2 基线） | glm-5.3-flash |
|---|---|---|
| converged_rate | 0.625 | **1.0** |
| first_pass_rate | 0.375–0.5 | **0.875** |
| 失败对 | 05/07/08 | 无 |

逐对轨迹的关键细节：

- **05/07 一次通过**：5.3-flash 直接**没有踩**需求里"（模型会先把 visible 写成字符串 'true'）"的坑——repair 场景根本没被触发。
- **08 两轮收敛**：第 1 轮真实产生了 `UNSUPPORTED_PLATFORM`（live_stream + ios，正是陷阱预告），第 2 轮在**完全相同的 v2 JSON 反馈格式**下选择"删组件保双端"，正确完成过约束松弛。

**结论**：v2 管线与反馈机制无缺陷；4-flash 的 repair 失败是**模型能力问题**。
同一反馈，5.3-flash 一轮修好，4-flash 六轮修不动。

## Q2：反馈模板升级（v2 JSON → directive：当前值+修正指令）能否救活 glm-4-flash 的 repair 类？

**假设**：v2 反馈只给错误码/路径/可选值；附上"当前值 + 怎么改"的显式指令应降低修正难度。

**实验**：A/B 同日同模型同 4 对（01 对照 + 05/07/08），`NL2CONFIG_FEEDBACK_STYLE=directive`。
代码开关：`violations.build_feedback(style=...)` + `llm._render_user`（默认 json=v2 逐字节不变，离线 42 测试锁定）。

**数据**（`evidence/ab-20261014-4flash-{json,directive}.json`）：

| 变体 | 05 | 07 | 08 | repair 类收敛 |
|---|---|---|---|---|
| json（v2，同日基线） | degraded | ok@3 | degraded | 1/3 |
| directive | degraded | ok@4 | degraded | 1/3 |

**轨迹解剖**（违规历史逐轮）：

- 05：4 轮 `WRONG_TYPE@visible` **原位重复**（json）；directive 下 r2 从 4 处降到 1 处，**r4 又回涨到 3 处**——部分服从后回退。
- 08：directive r3 一度修好 `UNSUPPORTED_PLATFORM`（只剩 TRACK_PARAM），**r4 平台违规复现**——振荡。
- 08 的 trackParams 键 `ch_ios_main`（ios 根本不是合法渠道）跨轮不改。

**结论**：directive 反馈**不能**救活 4-flash 的 repair 类（1/3 → 1/3）；它能让单轮违规数下降，
但无法阻止回退/振荡——反馈吸收是不稳定的能力，不是信息不足。

## Q3：few-shot 完整合法示例注入能否救活？

**假设**：给一个通过全部校验的完整配置示例（`examples/site.json`），模型可模仿格式消除结构类错误。

**实验**：`NL2CONFIG_FEW_SHOT=1`（system prompt 追加完整合法示例，+815 字符），同 4 对。

**数据**（`evidence/ab-20261014-4flash-fewshot.json`）：

| 变体 | 05 | 07 | 08 | repair 类收敛 |
|---|---|---|---|---|
| json 基线 | degraded | ok@3 | degraded | 1/3 |
| few-shot | degraded | degraded | degraded | **0/3** |

**结论**：few-shot **负收益**（07 也被拖挂）。对被对抗性元指令锚定的任务，
示例模仿打不过指令锚定；且更长 prompt 未提升格式保真。小模型上 few-shot 不是万能药。

## Q4：max_retries 3→5 的边际收益？

**假设**：若失败是"差一点就收敛"，加轮数应有效；若是顽疾/振荡，加轮数只是重复失败。

**实验**：json 基线 + max_retries=5，仅 05/07/08。

**数据**（`evidence/ab-20261014-4flash-json-r5.json`）：

| 变体 | 05 | 07 | 08 |
|---|---|---|---|
| retries=3 | degraded@4 | ok@3 | degraded@4 |
| retries=5 | degraded@6 | ok@5 | degraded@6 |

05 在 6 轮内 `WRONG_TYPE@visible` **逐轮原位重复、零次修复成功**；08 六轮同样的
`UNSUPPORTED_PLATFORM + TRACK_PARAM_FORMAT` 组合纹丝不动。

**结论**：重试上限翻倍对 05/08 **零边际收益**——失败不是轮数不够，是单轮修正能力缺失。
（07 在 3~5 轮间摇摆收敛，属输出非确定性，见 Q6。）

## Q5：repair 类失败的两个候选机制——"对抗性指令锚定" vs "过约束推理失败"（分离实验）

**假设**：05/08 的需求文本自带"（模型会先把…）"元指令且每轮重注入。若失败主因是该指令**锚定**，
剥离后裸输出应变干净；若模型真的不具备该约束的推理能力，剥离后仍失败。

**实验**：`evidence/anchor_probe.py`——同一 pair 两 arm（trap=原文 / clean=剥离括号），
各 4 次单发采样（不进修复循环），统计第 1 轮裸输出违规。

**数据**（`evidence/anchor-20261014-4flash.json`，glm-4-flash）：

| pair / arm | first_pass_ok | visible 布尔率 | 违规码分布 |
|---|---|---|---|
| 05 trap | 0/4 | **0%** | WRONG_TYPE×12（每样本全组件字符串 visible） |
| 05 clean | **4/4** | **100%** | 无 |
| 08 trap | 0/4 | 100% | UNSUPPORTED_PLATFORM×4 + TRACK_PARAM×3 |
| 08 clean | 0/4 | 100% | UNSUPPORTED_PLATFORM×4 + MODULE_NOT_IN_PACKAGE×1 |

**结论（机制分离）**：

1. **05 = 纯锚定**：clean 需求下 4-flash 一次输出全部布尔正确——它**完全具备**输出
   `visible: true` 的能力；失败唯一根因是对抗性元指令在每轮重注入下压倒了
   逐字段显式反馈。反馈修不动不是"不会改"，是"指令优先级压不下去"。
2. **08 = 真实过约束推理失败**：clean 需求（"双端站配直播组件"）下**仍 0/4**
   撞 `UNSUPPORTED_PLATFORM`——需求本身过约束（live_stream 仅 android），
   合法解必须主动松弛一端（弃 ios 或弃组件）。4-flash 无此判断力（Q2 数据：
   即使反馈明说"二选一"仍六轮不收敛）；5.3-flash 第 1 轮踩坑后 1 轮反馈即完成松弛（Q1）。

## Q6：temperature≈0 能否让输出可复现（科学复现性问题）？

**假设**：若 API 在 temperature=0.01 下逐字节稳定，则实验可复现，失败/成功可严格归因；
若不稳定，则单次采样的 pass/fail 只能做统计解释。

**实验**：`evidence/stability_probe.py --mode temp0`——同一 prompt 直连 ×3，比对最终
content 的 SHA256。

**数据**（`evidence/temp0-20261014-4flash.json`）：3 次采样 **3 个不同 hash**
（f1828022… / 518119a3… / 267cfb48…，长度 844/733/818）。

**结论**：temperature≈0 下输出仍**非逐字节确定**（MoE 路由/批调度等基础设施级随机性，
与采样温度无关）。推论：golden 收敛率本质是**随机变量的观测**（Q1 里 07 在 3~5 轮间摇摆、
Q2 里 json/directive 的 07 分别 ok@3/ok@4 同源）；任何单轮 pass/fail 不能作为确定性回归判据，
只能以比率+违规码分布做统计口径——这正是 golden.py 以"校验全绿"而非逐字段相等为判据的根因。

## Q7：双模型首发格式保真度基准（中立复杂需求，量化参数规模差）

**假设**：强模型在格式保真（结构/类型/键格式）上应全面 ≥ 小模型。

**实验**：`evidence/fmt_fidelity_bench.py`——不进修复循环，同一复合需求
（三页×多组件×双渠道追踪）单发采样各 10 次。

**数据**（`evidence/fmtbench-20261014-{4flash,5flash}.json`）：

| 指标（首发生成） | glm-4-flash | glm-5.3-flash |
|---|---|---|
| parse_ok / structure_ok | 100% / 100% | 100% / 100% |
| visible 布尔率 / trackParams 合规率 | 100% / 100% | 100% / 100% |
| **深层全绿率**（含引用/语义/业务） | **10/10** | **8/10** |
| 平均时延 | 21.6s | 27.2s（reasoning） |

**结论**：**假设被证伪**。中立需求下 4-flash 首发格式保真满分；5.3-flash 反而
2/10 失败（失败模式见 Q8）。"更强模型=更守格式"不成立——格式字面遵循与推理深度
是两种能力，4-flash 恰因"更听话"而更保真。

## Q8：5.3-flash 的首发失败模式解剖（ID 实例化改写）

**假设**：Q7 中 5.3-flash 的 INVALID_COMPONENT_ID 不是随机幻觉，而是系统性模式。

**实验**：同需求再采 6 次，捕获配置定位幻觉 ID 形态
（`evidence/hallucination-ids-5flash-20261014.json`）。

**数据**：6 次 × 2 次失败（33%），两种系统性模式：

1. **全量 `_1` 后缀实例化**：`video_player_1` / `mall_shop_1` …——把注册表 ID 整体
   当作"类型名"自行加实例编号（多实例需求触发"去重编号"直觉）；
2. **自由语义 ID 发明**：`home_video` / `profile_mall` / `community_feed`——按页面语义
   造新 ID，无视资产注册表白名单。

两种都是**规则级改写**而非知识缺乏（system prompt 已列出全部合法 ID）。
但注意与 Q1 互补：5.3-flash 的幻觉**可被 1 轮结构化反馈修复**（golden 04 两轮收敛、
Q1-08 一轮修复平台违规）；4-flash 的锚定/过约束失败 **6 轮反馈修不动**（Q2/Q4）。

**结论**：两代模型的短板分别在光谱两端——4-flash：**首发射得准，但反馈吸收失效**
（指令锚定压不下去、过约束不会松弛）；5.3-flash：**首发会自作主张改写格式，
但反馈吸收强**。校验-修复循环恰好把两者都兜住（这正是本管线的设计价值）。

## 总瓶颈结论（当前 AI 模型能力真实上限）

**一句话**：在"反馈修不动"的意义上，小模型（glm-4-flash）的真实上限是
**反馈吸收能力**——对抗性指令锚定与过约束松弛两类失败，对"模板升级/few-shot/
重试加倍"全部免疫（Q2/Q3/Q4 六轮零修复），而 5.3-flash 用**同一份 v2 反馈**一轮修好
（Q1）；同时输出在 temperature≈0 下仍非逐字节确定（Q6，基础设施级随机性），
故收敛率只能作为统计量而非确定性回归判据。

证据链（全部可复现，命令见各节）：

1. Q1 强模型全量 golden 8/8（converged 1.0），4-flash 同 prompt 稳定卡 05/08；
2. Q2/Q3/Q4 三种工程手段对 4-flash 的 05/08 收敛率 0 改善（few-shot 还负收益）；
3. Q5 机制分离：05=锚定（clean 需求下布尔率 100%）、08=过约束推理失败（clean 仍 0/4）；
4. Q6 temp0.01 三次采样三个 hash；
5. Q7/Q8 强模型自身另有 ~20–33% 的系统性 ID 改写失败模式（可被反馈修复）。

**工程对策结论**：不值得为 4-flash 继续加 prompt 工程（边际收益为 0 或负）；
正确姿势是本管线已有的"校验拦截 + 有限重试 + 显式降级转人工"，以及按场景路由
——对抗性/过约束需求直接用强模型或转人工。
